# Use the destination's real disclosure

Preserve the user's chosen app and format. Do not build a website just because the source is long.

## Linear and other issue trackers

Use native collapsible sections when the editor and write path support them. Linear's [editor documentation](https://linear.app/docs/editor) describes `/collapsible section` and `>>>` followed by Space. Those are editor operations, not a guarantee that an API accepts HTML or the same syntax. Check current capability through the app's docs/tools; test saving and reopening before a batch rewrite.

If the available write path cannot preserve native disclosure, use concise descriptions with descriptive links to existing protected documents or a supported linked section. Do not write literal `<details>` tags and call them toggles. When preparing a draft without an editor, label the proposed destinations as proposals rather than simulating working controls.

For a batch, first verify one representative saved item. Preserve original descriptions in a private task artifact, compare current update identity/content before each write, and stop on a conflicting edit. Keep comments, attachments, relationships, status and assignments intact unless their change is requested. Do not send progress comments as an incidental copy-edit.

## Chat, Markdown, docs and email

Use real supported disclosure if present. Otherwise put the short brief first and link to actual sections, attachments or existing documents. If links cannot be created, put clearly titled detail below and state that it scrolls; do not call the whole message one-screen. An ordinary chat answer need not invent an artifact to make a short point.

For a plain email, a brief plus a document link is more reliable than interactive markup. Drafting an email does not authorize sending it. Preserve access restrictions on linked material.

For a full contract, procedure, tutorial or specification, preserve the continuous source and create a short entry brief. Confirm scope before changing legally or operationally binding wording. A request to shorten wording losslessly is not permission to remove requirements.

## Standalone HTML or an existing web interface

Use semantic headings, links and native `details`/`summary` for independent optional sections. Start sections collapsed unless the user needs them immediately. Keep labels visible, descriptive and touch-friendly. Provide a clear way back from lengthy detail. Avoid nested disclosure and horizontal tables on a narrow viewport.

Use the project's existing components when applicable. For a standalone artifact, a single column usually spends less width on wrapping than a dashboard grid. Start with at least 16 CSS-pixel body text, comfortable line spacing and 44-by-44 CSS-pixel interactive targets. Use safe-area-aware padding and normal document overflow. Preserve content and navigation without JavaScript when practical.

Create visuals only when they explain something faster than prose. They consume screen space too. Use real captured media for claimed app results; label synthetic illustrations. Avoid external fonts, trackers and unnecessary embeds in a shareable brief.

The previous phone-roll JSON schema and renderer are not required. Its four fixed fields and three-to-five routes are intentionally replaced by content-dependent structure. Retain source facts and links, not its internal field names.
