# Access and Verification

## Access

- Start with the direct public listing or calendar and use what the audience can see. Use the organizer's authorized connector or host view for private fields and confirm the managing calendar and host access. A listing on a calendar may be an external submission the calendar operator cannot edit. Distinguish rate limits, fetch or parsing failures, and an event confirmed missing. When you have only a dated receipt, report its date and the limits of that evidence.
- If browser access is needed, use a persistent, signed-in browser session the organizer set up. Check that it reaches the right host view. If it redirects to sign-in, let the organizer sign in through the ordinary interface. If the host view remains unavailable, deliver paste-ready fields and identify which values still need to be checked.
- Use the editor's visible controls. When replacing formatted copy, select and clear the existing content before pasting. Use the visible controls for required questions and the cover upload. Reload and check the saved content, question types and requiredness, and image.
- If a browser challenge or send error blocks an invitation, pause and inspect the host send record before any retry. If the challenge persists, have the organizer confirm the recorded audience and complete the send in the normal host interface. Compare the actual and intended audiences afterward. Resolve missing or unexpected entries before another send. Record an uncertain send as pending verification.

## Read Back at the Destination

- Check the authoritative saved state after a fresh load or read. Compare the event ID and calendar, date and time zone, venue or Virtual setting, visibility, host roles, approval, cap, waitlist, question types and requirements, guest state, and queued notices as relevant.
- Inspect the signed-out event and calendar if the result should be visible there. Follow the exact registration path to the point before submission. Use the approved-guest or host view to verify restricted fields and access, and keep private links and identities out of the receipt.
- For messages, compare the destination's send or scheduling record and audience with the scoped action. A pending invite and an accepted invite describe different states. Record delivery or acceptance only when there is evidence for it.

## Receipt Template

- **Checked at** — date, time, and time zone
- **Destination** — event link or ID, managing calendar, and other destination checked, if relevant
- **Authorized scope** — specific fields or action, audience, and any automatic notifications
- **Changes attempted** — fields and before → intended values, or action and resulting record ID if available
- **Observed state** — read-back values and applicable state such as created, saved, public, draft, scheduled, sent, accepted, or checked in
- **Checks run** — host read-back, audience view, link test, or send record, with result
- **Pending** — outstanding approval, blocker, unknown state, or remaining decision
