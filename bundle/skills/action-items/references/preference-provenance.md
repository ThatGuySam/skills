# Preference Provenance

This skill was written in October 2026 from a correction ledger built from Sam's real meeting follow-up work: direct user corrections in agent chats, the artifacts those chats produced, and later reviews. The ledger and its source meetings are private and are not part of this repository; maintainers keep the full provenance, with the quoted corrections, in the private companion repository under `evals/sams-action-items/`. Normal use is self-contained.

The ledger separates direct user corrections from authored artifacts, contextual meeting attribution, and researcher observations. Its case groups are neither unique mistake counts nor a complete history.

| Behavior | Evidence | Scope |
| --- | --- | --- |
| Read the actual discussion and ground each recipient task | Repeated direct corrections and supporting artifacts | General. |
| Preserve accepted work while recovering implied requirements | Direct corrections | Interpret context without turning incremental requests into a rebuild. |
| Reconcile plans, closed work, and newer corrections | Direct corrections and artifacts | Preserve chronology and evidence of current state. |
| Resolve source-retrievable questions before asking again | Direct corrections | Consequential unanswered choices still need a question. |
| Separate preparation from execution | Direct correction | Current explicit authority decides what may happen. |
| Keep the first view short and keep requirements and history | Direct corrections | Fixed item counts from single tasks are not general rules. |
| Avoid unnecessary partner approval work | Direct corrections | One project's completion and release rules must not become global defaults. |
| Keep ownership, names, dates, and completion evidence accurate | Corrections and researcher findings | Attribution gaps and researcher-found errors are not direct user preferences. |

For preference conflicts, current explicit instructions outrank inferred habits. Apply project-specific rules only in that project. A question asking for an explanation is not automatically a correction. An unknown speaker label or recorder identity does not show who made a statement.

## Chat, not a file

After the first prototype, Sam rejected its length and file-based delivery: the action items belong in the current thread, not in a file of their own, and should fit one phone screen. Saved action documents need an explicit request.

## Tiny trees

Sam approved short per-meeting trees, then asked for a little more detail as tiny trees about two levels deep. Use `sams-tree` for structure, with two displayed levels overriding its general three-level default. Each meeting gets its own name and date, meaningful markers, concrete subtasks, and a short caveat where needed. Grouping by familiar work or by owner are both valid. This approval concerns presentation; it does not authorize carrying out the listed actions.

## Verbatim notes and actionable meaning

Sam asked to keep his own notes word for word, layer the rest beneath them, and return one copyable list with the original hierarchy and scannable emoji. Transcript-only actions join the same tree with an inline source label instead of a separate list.

In one meeting, an already-listed email action had lost a requirement: the message needed to document access limits and reliance on other tools so the recipient could pursue support. In a blind subagent trial on that meeting, the revised instructions kept the requirement and the earlier version lost it, including at similar output lengths. This supports that specific recovery, not broad reliability. A word target must never erase a requested channel, purpose, dependency, or later clarification.
